# `@ewaste/datasets` — dataset card

Structured datasets for the collector platform, plus the generator, validator
and evaluation harness that produce and police them.

> **Every record in `data/` is synthetic.** No real collector, facility,
> transaction or phone number is represented. Seeded facilities carry a
> `[Demo]` name prefix and a `SYN/` authorisation number so a synthetic record
> can never be mistaken for a genuinely authorised recycler. Before any pilot,
> `recyclers.json` must be replaced with records taken from the relevant State
> Pollution Control Board / CPCB authorisation lists.

## Why synthetic seed data at all

The platform's datasets are meant to be *generated by field operations* — that
is the point of the product. But the app, the API, the price board and the
matcher all need realistically-shaped data before the first collector installs
anything. So the seed exists to:

1. exercise the whole pipeline (generate → validate → index → serve → score)
   end to end, so the code that will one day handle field data is already
   written and tested;
2. give the rule-based services a measurable baseline before any model exists;
3. let a reviewer run the demo with no backend setup.

It is **not** a substitute for field data, and nothing in it should be quoted
as a market fact.

| File | Rows | What it is |
| --- | --- | --- |
| `meta.json` | — | Generator version, seed, window. Provenance for every other file. |
| `recyclers.json` | 21 | Recycler dataset: facility, materials accepted, authorisation, rate card, pickup, service area. |
| `prices.csv` | ~16,600 | Price dataset: category, sub-category, district, timestamp, buying price, quoted price, unit, market band, source, confidence. |

| `lots.csv` | 1,400 | Lot header: collector, status, weight, estimated value, collection place and time. |
| `materials.csv` | ~2,650 | Material dataset: category, sub-category, image ref, weight, condition, source type, estimated value. |
| `transactions.csv` | ~1,040 | Transaction dataset: lot, collector, recycler, quoted vs final price, payment status/mode, anomaly flags. |
| `traceability.csv` | ~1,040 | Traceability dataset: handover ref, digest, photo hashes, declared vs weighed weight, GPS, confirmation, downstream status. |
| `training_manifest.csv` | ~2,650 | AI/ML manifest: image ref + label + weight + district + settled price, with a deterministic train/val/test split. |
| `anomaly_ground_truth.csv` | 56 | Which transactions were deliberately made bad, and how. Used to score the detector. |
| `price_index.json` | — | Derived artefact: the compact per-district price summary that ships to phones for offline valuation. |

Total ≈ 4.2 MB. CSV throughout, so every file opens in a spreadsheet.

## How the data is generated

`src/generate.ts`, driven by a seeded PRNG (`src/random.ts`). Same seed, same
bytes — a diff in `data/` means the generator changed, not the dice.

Realism comes from three modelled effects rather than uniform noise:

- **A shared commodity index per metal group.** Copper-bearing categories move
  together across the year, as they do in the real scrap market; battery metals
  and rare earths are the volatile groups, glass barely moves. Without this,
  price "trends" would be pure noise and the trend feature would be untestable.
- **A district price factor.** Prices near processing capacity are higher, so
  location genuinely matters to the matcher instead of being decoration.
- **Deliberate bad transactions** (~5%): underpayment, weight shortfall at the
  scale, and reused photographs — recorded in `anomaly_ground_truth.csv` so the
  detector is *scored*, not merely demonstrated.

Observations are sparse and irregular (roughly one per sub-category, district
and day at 20% probability), because field price collection is sparse and
irregular.

```bash
pnpm data:generate                                   # default seed, 365 days
pnpm data:generate -- --seed 42 --days 180 --lots 500
```

## How it is validated

`pnpm data:validate` runs 22 checks and exits non-zero on any error, so CI can
gate on it:

- **Schema conformance** — every row of every dataset against the zod schemas
  in `src/schemas.ts`. Those same schemas validate sync pushes from phones and
  rate updates from recyclers, so the seed and the field share one contract.
- **Referential integrity** — nine foreign-key relationships (materials → lots,
  transactions → recyclers, traceability → transactions, and so on).
- **Cryptographic integrity** — all ~1,040 handover digests are re-verified.
  A traceability record whose digest does not recompute is worthless.
- **Coverage** — every one of the 28 sub-categories has price observations,
  and thin district cells are reported as warnings (they fall back to the
  national rollup by design).
- **Uniqueness** — no duplicate primary keys in any dataset.
- **Split hygiene** — no image hash appears in more than one train/val/test
  split. A leak here would make any reported accuracy meaningless.
- **Provenance** — every seeded facility is marked synthetic.
- **Reconciliation** — collector lifetime-earnings counters must agree with the
  transactions they summarise.

## How it is scored

`node --experimental-transform-types scripts/evaluate.ts` measures the
rule-based services against the ground truth:

```
Anomaly detection vs injected ground truth
  transactions        1042
  injected anomalies  56
  flagged             57
  true positives      56      false positives 1      false negatives 0
  precision           0.982   recall 1.000           f1 0.991

  recall by injected kind
    underpayment       24/24   weight_shortfall 12/12   duplicate_photo 20/20

Valuation estimate vs settled price (clean transactions only)
  median error 4.7%   mean absolute error 5.5%   within 20%: 99.9%
```

**Read these numbers correctly.** They score the rules against synthetic data
produced by a related process, so they are a *regression baseline* — they prove
the rules are wired up and catch what they are meant to catch, and they will
fail loudly if a rule breaks. They are not field accuracy, and must not be
presented as such. Real precision and recall can only come from labelled field
transactions.

The harness earned its place during development: it caught two genuine defects
that all 22 validation checks had missed.

- The anomaly detector computed its fair-value baseline from raw median rates
  while the app's valuer applied condition discounts, so every legitimately
  discounted lot — broken, burnt, wet — read as underpayment. 259 of 1,042
  transactions were falsely flagged (precision 0.15). Warning a collector that
  an honest offer is a rip-off is the fastest way to lose their trust, so the
  fair-value baseline now comes from the same `Valuer` the app showed them.
- Duplicate-photo detection never ran, because the known-hash set was never
  passed to it. Recall on that class was 0.15 and the rule was effectively dead
  code.

## Known limitations

1. **No images exist.** `training_manifest.csv` lists image *references* with
   labels, weights and settled prices — the photographs themselves are not in
   this repository and cannot be synthesised honestly. Any image classifier
   needs real field photographs first; see `docs/ai-ml.md`.
2. **Prices are modelled, not observed.** Reference bands come from published
   ranges for Indian e-waste scrap and are plausible, not authoritative. The
   day-to-day movement is a random walk, not a real commodity series.
3. **Recyclers are fictional.** Facility names, locations, authorisation
   numbers and rate cards are invented.
4. **Anomaly ground truth is generous.** The detector is scored on the exact
   failure modes the generator injects. Real fraud will include kinds nobody
   modelled, and the true false-positive rate on field data will be higher.
5. **Geography is coarse.** Coordinates are district centroids with jitter, not
   real facility addresses; distances are therefore indicative.
6. **Eight districts, six in Maharashtra.** The national rollup is thin and
   should not be treated as an all-India price signal.
7. **No seasonality or festival effects**, which materially move scrap volumes
   in practice.
8. **Collector behaviour is simplified** — no repeat relationships with
   particular buyers, no route structure, no seasonal absence.

## How the data is updated in production

The seed is the starting point, not the mechanism. In the field:

- every completed transaction writes a `completed_transaction` price point
  (the highest-confidence source), so the price dataset grows from real
  settlements rather than scraped boards;
- every recycler correction to a collector's category becomes a
  `recycler_corrected` training label — the single most valuable record the
  platform produces;
- the price index is rebuilt nightly per district and shipped to phones on next
  sync (a few KB), which is what makes offline valuation possible;
- validation runs on every ingest, not only at generation time. A dataset
  validated once at build time drifts the moment real data arrives.
